Every page, every path, every piece of functionality behind them.
Reconciled against the full role-by-role route spec (shared shell, provisioning chain, and the four role portals) and kept in the same route-by-route format as your TRUST guide. Every route below traces back to that spec.

Revision 2. Adds the trial-period validation chain (§2.3, §2.5, §3, §4) and department-targeted document publishing (§2.3, §3). Everything new carries a New badge so this revision can be read as a diff against the first.

0. How to read this document

Every route below is tagged:

  • Core — the actual product: the provisioning chain, the parcours engine, and the five AI agents talking to real (or mock) data. Needed for any working demo to Mostapha / Djaoudi. Build these first.
  • Site — needed so the platform looks and feels like a finished tool when someone clicks around, but isn't part of the core "agents + parcours" story.
  • Later — real production scope, correctly out of scope until SOFICLEF opens the access it depends on.
  • New — added in revision 2; see the note at the top.

A Chain badge next to a route means it's built and fully working now on mock data or on content pulled from SOFICLEF's public website — and is a chaining point later: per the CDC's Plug & Play clause, going live means pointing that one route at the real data source, not rebuilding it. No route carrying that badge needs new code written when the real data shows up, only its adapter re-pointed (see Section 5).

Suggested stack, matching what the CDC specifies: React / Next.js with Tailwind or Bootstrap for every page below, Node.js or ASP.NET Core for the routes in Section 3, Azure OpenAI / Copilot Studio / Azure AI Foundry behind the agent routes in Section 4, and Microsoft Entra ID / Active Directory for auth once it's wired in.

0.1 Shared authenticated shell

All four roles sit inside the same shell: a top bar with global search, a notification bell (delays, pending tasks, surveys), a language switcher (FR/EN/AR), and a profile menu with a role switcher. The left sidebar changes per role. A persistent AI chat drawer is docked bottom-right — which of the five agents answers there depends on the active role.

Three routes are truly shared, not role-scoped — they render the same shell chrome no matter who's logged in:

PathTagPurpose
/app/profileSitePersonal account settings, plus the role switcher for anyone holding more than one role
/app/notificationsSiteDelays, pending tasks, survey reminders — feeds the top-bar bell

Org chart and documents are conceptually "every role has one," but the content and permissions differ enough per role that each gets its own page instead — see /app/me/organigram vs. /app/hr/organigram, and /app/me/documents vs. /app/hr/documents, in Section 2.

0.2 The provisioning chain

This is the backbone of the whole platform — worth stating before any page list, because it decides what every other route is allowed to show.

  1. SI / Admin creates the account in Entra ID / AD — sets professional email, phone, platform role → account state CREATED — AWAITING ASSIGNMENT
  2. HR assigns position, division/department, direct manager, hire date, onboarding template, and equipment → account state ASSIGNED, the path is generated and the org node is placed
  3. New hire logs in for the first time → welcome wizard → their own dashboard and org chart

Three consequences to build around, all Core:

  • No path exists before HR assignment. A user who logs in while still at state 1 lands on /pending — a message and a contact link to HR, nothing else. No sidebar, no documents, no assistant.
  • HR can request, not create. HR's "Request an account" button opens a ticket to SI (name, position, planned hire date). HR keeps the initiative on hiring without ever holding account-creation permission — the exact separation the CDC's security section asks for.
  • Reassignment is HR's, permanently. Changing position, manager, or department after onboarding is an HR action that moves the org-chart node and may adjust the remaining path. SI never touches it.

0.3 The evaluation chain New

The trial period has its own chain, and it is deliberately separate from the provisioning one. It answers a different question — not "may this account be used" but "does this person stay".

  1. The responsable evaluates. Whoever has people under them evaluates the ones under them: the subject's managerId is the evaluator, not a role held in the abstract. They score four criteria (skills, autonomy, integration, behaviour) from 1 to 5 and submit.
  2. The platform computes, and only suggests. The four scores give a percentage out of 20, which maps to a suggested outcome by the thresholds in §2.5.
  3. HR decides. HR sees the result — score, percentage, suggestion, and the responsable's own recommendation — and applies an outcome. HR may depart from the suggestion, and must give a reason when they do.

Why HR confirms rather than the system deciding. Ending someone's employment must not be an automatic side-effect of arithmetic. The percentage is evidence a human acts on, and the decision — including any departure from the suggestion — is recorded with its author and its reason. A score alone has never been a dismissal.

2.5 Trial-period validation, end to end New

Three actors, one direction of travel, and no step that can be skipped. Every stage is separately authorised, so no single person can both score and decide.

Who evaluates whom

The rule is structural, not a role check: whoever has people under them evaluates the ones under them. The subject's managerId names the responsable, and the platform refuses an evaluation submitted by anyone who is neither that person nor covered by the same organizational scope. A manager with nobody under them evaluates nobody. Reassigning someone to a new manager moves the obligation with them — it is the same field the org chart reads.

The scoring

Four criteria — skills, autonomy, integration, behaviour — each rated 1 to 5, giving a total out of 20. The percentage is total / 20 × 100, and it is recomputed on the server at decision time; a score arriving from a client is never trusted.

  • > 60 %ConfirmThe trial period ends successfully; the collaborator is confirmed in post.
  • 30 – 60 %ExtendThe trial period is prolonged; a further evaluation follows at the new end date.
  • < 30 %TerminateThe trial period ends without confirmation. Never applied without an explicit HR action.

The boundaries, stated once. Above 60 confirms. From 30 to 60 inclusive extends. Below 30 terminates. The bands are exposed by the API as a constant so the interface and the server never drift into disagreeing about a borderline case.

What each actor sees

ActorSeesCan do
Responsable
the subject's manager		The evaluation form for people who report to him; his own past submissionsScore the four criteria, comment, recommend an outcome, submit. Cannot apply the outcome.
HRThe result only — scores, percentage, suggestion, and the responsable's recommendation. Not the form.Apply confirm / extend / terminate. Depart from the suggestion, with a recorded reason.
The collaboratorNothing, in this portalNothing. The outcome reaches them through their responsable and HR, not a dashboard tile.

Rules the implementation enforces

  • A decision is refused if the instance already carries a non-ONGOING outcome — the trial period is decided once, and a change of mind is a new, separately audited act.
  • reasonFr is required whenever the applied outcome differs from the suggested one. Agreeing with the arithmetic needs no justification; overriding it does.
  • The percentage and the suggestion are recomputed server-side from the stored scores at the moment of decision.
  • Every decision writes a ProbationDecision row — score, suggestion, applied outcome, reason, author, timestamp — and an audit entry. The history is readable per recruit.

2.6 Document publishing and audience New

Until this revision every document in the library was visible to everyone who could read documents. Publishing now carries an audience.

  • All staff — the previous behaviour, still the default.
  • Named departments — the document appears only in the accounts of people in those departments, matched against the person's division or service. Accepting a document for the HR department publishes it to every HR account, which is the case that prompted this.

HR and Admin always see every document regardless of audience: you cannot manage a library whose contents are hidden from you. The audience narrows who receives a document, not who administers it.

Audience is not access control. It decides which library a person's /app/me/documents shows, and it is enforced in the query rather than in the interface. It is not a confidentiality boundary for material that must not leave a department — that would need a classification on the document and a rule at the storage layer, neither of which exists today.

5. Cross-cutting functionality, not tied to one route

The provisioning chain is one seam, not three separate checks. "No path before assignment," "HR requests but can't create," and "reassignment is HR's alone" are all enforced inside internal/provisioning/state-machine and internal/rbac/guard — not as scattered if role == checks sprinkled through /pending, /app/hr/employees/request, and /app/hr/employees/[id]. Add a fifth role later without touching those three pages.

The evaluation chain is a second seam of the same kind. New "The responsable evaluates," "HR decides," and "a divergence needs a reason" live in internal/probation/* and the same RBAC guard — never as a role test inside the evaluation form or the probation page. The consequence worth stating: the interface can be rebuilt, or a fifth actor added to the chain, without any of those three rules moving.

One seam per data type, not a hundred rewrites. Every route carrying the Chain badge reads its data through a thin adapter — one for the knowledge base, one for the org-chart directory, one for documents. Flipping /admin/integrations later means pointing three adapters at Entra ID/AD and SOFICLEF's real document store, never touching the route code above them. That's the CDC's Plug & Play clause; the discipline is keeping every mock-vs-real decision inside the adapter.

Source citation is enforced once. internal/knowledge/retrieve is the only place any agent touches the document base, so the "must cite its source" requirement lives there — not duplicated separately inside Agents 1, 3, and 4. /app/hr/ai-knowledge is the one screen that lets HR test and audit it.

One org tree, four readers. The self-centered tree (/app/me/organigram), the sub-tree expansion (/app/manager/organigram), the whole-company view with drag-reassign (/app/hr/organigram) and — since revision 2 — the responsable lookup behind every evaluation all read the same internal/org-chart/tree. A reassignment made in one view is immediately correct in the others, and immediately moves who evaluates whom. New

Two renderings of one task list. A journey task shows up as a checklist item (/app/me/journey), a progress bar (/app/manager/recruits/[id]), and a completion-rate number (/app/hr/analytics) — all three read the same tasks table so they can't drift out of sync.

An outcome is written once and read everywhere. New The trial-period result is a field on the onboarding instance, so the recruit card (/app/manager/recruits), the employee record (/app/hr/employees/[id]), the turnover figure (/app/hr/analytics) and the audit trail all describe the same decision rather than four approximations of it.

6. What this means for the build

Everything tagged Core across Sections 2–4 is the real build list: the provisioning chain end to end (create → assign → first login), the journey engine, the org-chart tree on mock data, the trial-period chain, and the agents talking to the mock knowledge base — exactly what the CDC's Plug & Play clause front-loads, since none of it depends on SOFICLEF granting access first.

Everything tagged Site rounds the platform out once Core works end to end — worth doing once there's something real to click through. Everything tagged Later (real Entra ID/AD wiring, the RBAC matrix editor, audit/security/backup/GDPR consoles, the conversational reporting layer) shouldn't get engineering time yet — note that it exists in the demo, and move on.
